# v0.3 系统与集群操作规格

本文件定义当前版本已实现的操作语义、验收路径与剩余边界。界面和终端访问相同对象；命令返回结果不能独立于设备、进程和任务状态。

## 对象与状态

| 对象 | 持久状态 | 影响 |
| --- | --- | --- |
| 服务单元 | 所属节点、安装状态、PID、active/inactive/failed、生效配置快照、配置代数、错误 | 可连接端点、守护进程、日志 |
| 节点代理 | Munge 密钥快照、slurmd 进程、GPU GRES、注册结果、维护状态 | 是否接受新作业、现有 Worker 是否存活 |
| 作业 | 配方与提交脚本快照、节点数、每节点 GPU 数、优先级、时间限制、分配、Worker | 资源竞争、显存、阶段耗时、检查点 |
| GPU | 节点与卡号、占用者、显存、计算利用率 | 不能同时分配给两个运行中的任务 |
| 检查点 | WRITING/COMMITTED/ABORTED、分片、字节进度、校验、训练状态 | 只有完整且校验通过的版本允许恢复 |

## 建设顺序

完成现场接线、上电、装机、netplan 和运行时后，先建设存储：

```bash
labctl install storage
systemctl start nfs-server
mount storage-01:/data /data
```

在 BMC 的“Slurm 集群”页安装 Slurm、分发 Munge 密钥、启动认证与节点代理，再启动控制器。也可以逐节点执行：

```bash
# 密钥分发由 BMC 中的显式操作完成
ssh control-01
systemctl start munge
systemctl start slurmctld
exit
ssh gpu-01
systemctl start munge
systemctl start slurmd
journalctl -u slurmd
exit
scontrol show nodes
```

对 gpu-02 至 gpu-04 重复启动。控制器可以在 Worker 未注册时运行；“控制器在线”与“节点可调度”是不同状态。

## 验收 A：保存配置与生效配置

1. 启动 nfs-server，记录 PID 和配置代数。
2. 修改 `/etc/foundry/storage.conf` 的 `bandwidth_gbps` 并保存。
3. 服务列表显示 `SAVED / NOT APPLIED`，运行时继续使用旧带宽。
4. `systemctl start nfs-server` 不改变运行中配置。
5. `systemctl daemon-reload` 不改变应用配置。
6. `systemctl reload nfs-server` 应用新带宽、增加代数、保留 PID。
7. 非法配置的 reload 被拒绝，旧配置继续服务；非法配置的 restart 则停止旧进程并进入 failed。

应用配置路径是当前项目覆盖的服务接口，并非完整发行版的所有配置文件。systemd 单元定义编辑尚未实现。

## 验收 B：GRES 注册失败与修复

1. 在 `/etc/slurm/slurm.conf` 将 `Gres=gpu:h100:8` 改为 `Gres=gpu:h100:4`。
2. 保存后，已有控制器暂时保留旧配置。
3. 执行 `scontrol reconfigure`。
4. 节点显示 `GRES mismatch: hardware=8 configured=4 detected=8`，新作业无法取得这些节点。
5. 在日志中查看注册拒绝证据。
6. 修正为 8，重新加载，节点恢复 IDLE。

另一个独立故障：修改单个节点的 Munge 密钥并重启该节点 munge，将产生认证拒绝；网络连通不能自动解决认证问题。

## 验收 C：资源竞争与维护

训练配方增加 `optimizer_offload: cpu`，将提交脚本设为两个节点、每节点八张卡：

```bash
#SBATCH --nodes=2
#SBATCH --gpus-per-node=8
#SBATCH --partition=compute
#SBATCH --time=48:00:00
srun torchrun --nproc_per_node=8 train.py
```

使用 `TP=8 / PP=2 / seq_length=1024`，重新预检后连续提交两个作业。它们分别占用不同的 16 张卡。第三个四节点作业进入 Resources 等待。

```bash
squeue
scontrol show job 24001
scontrol update JobId=24003 Priority=500
scontrol hold 24003
scontrol release 24003
scontrol update NodeName=gpu-04 State=DRAIN Reason=maintenance
scontrol update NodeName=gpu-04 State=RESUME
```

维护状态阻止新分配，已经取得资源的作业继续执行。取消、超时、失败以及最终检查点提交完成后，释放对应 GPU。推理 Deployment 也占用同一份 GPU 台账。

CPU optimizer offload 在本版中影响显存估算和优化器耗时；尚未建立主机内存、PCIe 竞争和 NUMA 的完整模型。

## 验收 D：检查点中断、损坏与恢复

1. 训练到至少两份 COMMITTED 检查点。
2. 下一次保存处于 WRITING 时停止 NFS 服务或断开存储管理网。
3. 当前写入变成 ABORTED，作业失败；已有完整检查点不被改写。
4. 在检查点详情注入最新完整版本的 rank-0 分片损坏。
5. 恢复存储并执行作业恢复。
6. 恢复日志记录跳过的未完成/损坏版本，选择前一份校验通过的版本。
7. 检查模型行为状态、优化器、RNG、数据游标和配方与该版本一致。

```bash
ckptctl list
ckptctl verify ckpt-24003-0000200
```

本版检查点采用阻塞保存：WRITING 期间保留 GPU 分配、停止训练步推进，完成全部分片后更新 latest 指针。分片文件保存虚拟产物描述和校验信息；不会在浏览器中分配 TB 级权重。

## 验收 E：工程存档

导出包含生效配置、进程、分配、分片文件和写入进度。导入后停留欢迎页时冻结工程，继续后推进。导入/重置触发刷新时，旧工程的自动保存不能覆盖新的存档。

开发者运行 `node verify-v3.cjs --fixture` 后，可通过 `node preview.mjs --qa` 的 `/__qa/` 页面下载验收工程，再从应用正常导入。该页面只由本机开发预览提供，不包含在发布 HTML 中。

## 验证与边界

自动验证覆盖服务快照、配置失败、逐节点认证/GRES、并行占用、优先级、hold/release、drain、故障影响范围、检查点中断与损坏、导入后写入续接、超时、后训练、评测和部署。

浏览器验证覆盖完整存档下载与导入、4/4 节点注册、Slurm 配置编辑与 GRES 注册失败/恢复、进程页、GPU 台账、终端状态与检查点详情。

尚未覆盖完整 Slurm 优先级算法、backfill 预留、抢占、公平份额、多控制器高可用、完整 Linux 权限与软件仓库、实际 Python/CUDA 执行。训练学习和语言生成仍采用前版受限机制，不能用本轮的系统改进代表这些部分也已完成。

操作语义参考：[systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html)、[Slurm scontrol](https://slurm.schedmd.com/scontrol.html)、[Megatron Bridge 检查点](https://docs.nvidia.com/nemo/megatron-bridge/latest/training/checkpointing.html)。
