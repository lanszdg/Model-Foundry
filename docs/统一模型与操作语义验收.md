# v0.8 · 统一模型与操作语义验收

本轮将模型结构、GPU 资源、检查点、模型转换和服务容量接到同一份规格。终端与 Tensor API 增加具体执行语义。专业流程的整体覆盖情况见 [100 项工程场景清单](工程场景完成度清单.md)。

## 同一份模型规格

工程中的 `/workspace/atlas/model-spec.json` 是新任务的模型入口，包含 target、precision 和 numeric。target 描述 Atlas 70B 目标结构；numeric 描述浏览器实际分配的算子参考结构。提交时一起冻结，后续编辑只影响新任务。

| 默认目标结构 | 数值 |
|---|---:|
| Decoder 层数 / hidden / intermediate | 80 / 8192 / 28672 |
| Query heads / KV heads / head dimension | 64 / 8 / 128 |
| 目标词表 / 最大上下文 | 128256 / 8192 |
| 命名张量数量 | 723 |
| 根据张量形状累加的参数数 | 70,553,706,496 |
| BF16 权重容量，十进制字节 | 141,107,412,992 |
| 权重、FP32 master、Adam m/v 检查点容量 | 987,751,890,944 |

旧入口 `/workspace/atlas/model.json` 保留为 numeric 兼容入口。只修改其中一份时，检查过程同步另一份；同时修改且数值结构冲突时，检查明确失败。正在执行的任务读取冻结快照。

默认 numeric 是 2 层、32 hidden、4 Q heads、1 KV head、256 上下文，实际词表来自所用 Tokenizer。它执行完整 decoder 前向反向，不能提供真实 70B 的参数容量与语言能力。目标 BF16 容量计算和浏览器 F64 数值计算分别保留，当前没有 BF16 数值舍入、溢出和 loss scaling 的完整执行语义。

## 张量、GPU 与检查点

模型清单逐项生成 embedding、每层 Norm、Q/K/V/O、gate/up/down、末层 Norm 和 LM head。线性层采用导出格式的 `[out, in]` 维度。

TP 按 Q/K/V、gate/up 的输出轴以及 O/down 的输入轴切分；Norm 在 TP 内复制。PP 按层范围分配，embedding 在首段，末层 Norm 和 LM head 在尾段。词表切分保留填充与有效区间。

训练页 → **模型蓝图** 可选择每张 GPU，检查本地 shape、轴区间、复制状态、梯度/优化器容量和该 rank 的检查点大小。冻结产物保存在 `/runs/<job>/model-spec.json` 与 `tensor-layout.json`。

检查点按有效所有权计算分片大小，TP 复制的 Norm 只写一份，优化器状态按 DP/CP 拆分。首尾阶段和中间阶段的分片可以不同；校验按每个 rank 的预期字节数进行。恢复沿用冻结规格、参数、Adam moments、RNG 和数据位置。

这些 rank 清单驱动资源和事件机制。浏览器数值内核仍执行有预算的完整参考模型，尚未实现数值张量真正按 TP/PP/CP 跨 rank 传递；这一项在清单中保持“部分实现”。

## 转换和推理容量

模型转换从冻结规格生成目标配置、全部张量清单与虚拟分片。加载时核对规格摘要、Tokenizer、每个张量的名字/形状/精度、分片内容与字节总量。

目标 70B 分片是虚拟工程文件及其元数据，不会写出 141 GB 的真实参数。数值参考模型另有实际 F64 safetensors 字节，可下载、重载并进行矩阵轴和内容摘要校验。

服务按目标结构计算权重与 KV 容量。每张 GPU 的每 Token KV 字节为：

```text
2 × layers × KV_heads × head_dim × dtype_bytes ÷ serving_TP
```

默认 serving TP=8 时是 **40,960 bytes/token/GPU**。监控区分 KV 预留容量和实际使用容量。KV 配置超出显存预算时在修改状态之前失败；灰度加载第二个版本同样检查共存预算，失败后主服务保持原配置。吞吐与延迟系数尚未完成真实 GPU 标定。

## 终端支持范围

终端操作只影响工程内的虚拟世界。

| 范围 | 本轮支持 |
|---|---|
| Shell 数据流 | 单/双引号、转义、环境变量、`$?`、`;`、`&&`、`||`、管道、输入与输出重定向、stderr、`pipefail` |
| 文本命令 | `echo`、`printf`、`cat`、`grep`、`head`、`tail`、`wc`、`true`、`false`、`export`、`env` |
| Slurm 查询 | `squeue` 的 job/state/partition/node/user 筛选和 format；`sacct` 的对应筛选、字段列表和 parsable 输出 |
| 批任务 | 支持清单内的 SBATCH 参数，job-name 实际进入任务；非法参数、格式、字段返回非零退出码 |
| 能力查看 | `foundryctl capabilities` 或 `foundryctl capabilities --json` |

这不是完整 Bash。命令替换、任意脚本语法、通用通配符与字段展开等不在支持清单中；不支持的调用明确报错。`squeue`/`sacct` 以外的历史命令也不因此获得完整软件兼容性。

可在工位终端执行：

```bash
printf "a\nb\na\n" | grep -n a | wc -l
# 2
squeue --not-a-real-option
echo $?
# 1
sacct -n -P -j 24012 -o JobID,State,ExitCode
# 验收工程中：24012|COMPLETED|0:0
```

## Tensor 支持范围

项目 Python 中的 Tensor 支持严格的 `view`/`reshape`、单个 `-1` 推导、分维 `flatten`、负索引、行索引、带 dim/keepdim 的 sum/mean，并将梯度传回原始数据。`float()` 实际舍入到 FP32。已支持方法接收对应关键字参数，非法形状、轴、参数和不支持的广播明确报错；原地索引写入尚未实现。

## 可复现验收

```bash
node verify.mjs
python verify-transformer-reference.py
node progress.mjs
node build.mjs
```

v0.8 内部检查共 795 项。另用 NumPy 独立实现 RMSNorm、复数 RoPE、因果 GQA、SwiGLU、logits 和 NLL，与内核对照。检查数量只说明受测行为，不代表场景完成率或真实软件兼容认证。

浏览器验收覆盖模型蓝图 rank 切换、管道结果、非法参数退出码、作业筛选，以及修改配方后通过内联 Worker 启动训练。体验包的 `工程存档/统一模型与终端工程.json` 是环境已建好、默认发布门槛保留、3 步训练完成且工程时钟暂停的分支。可从 Code 修改配方并重新检查提交，或返回空机房建设完整环境。

## 目前最主要的剩余差距

逐 rank 数值分片、混合精度数值语义、工业二进制数据格式、完整容器与权限隔离、LoRA/量化/MoE、真实软件界面的操作覆盖和 GPU 性能标定尚未全部完成。100 项清单保留 34 项部分实现、17 项未实现；当前 49% 是固定条目内的内部闭环率，全部真实工程的 1∶1 复刻程度仍需外部逐项对照验收。
