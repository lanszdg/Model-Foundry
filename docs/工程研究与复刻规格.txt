大语言模型工程调研与复刻规格
调研日期：2026年11月26日
文档性质：开发前的工程研究与目标行为规格。本文包含长期覆盖目标，不作为当前版本已实现能力清单；v0.4 的可用能力与执行边界见 README、CHANGELOG 和执行与推理验收文档。

一、工程定位与复刻基准

目标是纯 HTML、CSS、JavaScript 的大语言模型工程工作台。所有环境与计算在浏览器内部仿真；用户进入的是同一套专业工作流，不区分入门版和专业版。业务界面使用实际工程的术语、文件、命令、日志、报错与状态，不反复添加“模拟”“教学”“小模型”等标识。

补充后的起点：玩家进入第一人称工程现场时，数据平台、集群调度、训练环境、模型仓库、监控与推理服务都没有预先搭好。项目需要实现这些系统本身，让玩家能够逐层安装、配置、启动、连接、验收、使用和维修。工具名称是工程语义参照；相应的系统行为、资源管理、文件、服务和接口由浏览器工程内部实现。

复刻单位是完整工程行为：操作改变项目状态，状态决定资源、日志和产物，产物成为下游输入，故障必须通过对应的工程操作修复。不能用互不相干的页面和任意下降的曲线代替整条工程链。

1∶1 的参照范围是公开可核查的专业工程接口与工作流程。不同机构使用不同工具，因此本项目固定一套参考架构，再对照公开的大模型全流程案例核查覆盖。不会把不同框架的参数、检查点格式和作业状态混为一谈。

拟定参考架构（属于本项目设计选型）：
  数据治理：NeMo Curator 工作流语义。
  分词与模板：Tokenizer 资产、模型对应的 Chat Template。
  预训练、继续预训练、SFT：Megatron Core / Megatron Bridge。
  后训练：NeMo RL，按算法组织 Policy、Reference、Rollout、Reward、Critic。
  训练调度：Slurm；后训练在已分配的资源内组织 Ray 工作进程。
  实验与模型资产：MLflow 的 Experiment、Run、Model Version、Alias 语义。
  推理：vLLM；服务发布使用 Kubernetes 的资源与发布语义。
  观测：训练日志、DCGM、Prometheus / Grafana、请求指标与事件。
  存储：对象存储、共享训练存储、节点本地缓存三个独立层级。

主项目场景拟设为 70B 级 Dense 大语言模型；MoE、长上下文、全量训练、LoRA 属于同一工作台内的架构或训练策略分支，不是不同难度版本。GPU 数量、训练语料规模与计算时长均由工程配置决定。

事实依据：NeMo 的官方模块覆盖数据、训练、对齐、评测和导出部署；Ai2 的 Olmo 3 公开案例提供预训练、mid-training、长上下文与后训练的完整模型流，可用于交叉核查阶段覆盖。这里选定的工具组合与界面结构是复刻设计，不声称它是 Olmo 的原始技术栈。[S01][S02]

二、工程不是一条只能向前的进度条

数据链：
  数据源登记 → 原始数据落盘 → 解析与质量审计 → 清洗与去重
  → 评测污染检查与数据切分 → Tokenizer / 模板绑定
  → 分词、打包、分片 → 冻结 Dataset Version。

基础设施链（与数据链并行）：
  设备与资源规划 → 装机与操作系统 → 网络、身份与时间同步
  → 存储服务建设 → GPU 驱动与容器运行时 → 镜像与软件环境
  → 调度服务安装配置 → 节点注册 → 通信与 I/O 验收。

平台建设链（依赖基础设施，建成对应组件后才能使用其功能）：
  元数据库与对象存储 → 数据接入和处理服务 → 数据平台
  → 训练工具链与实验追踪 → 检查点和模型仓库
  → 评测执行服务 → 推理运行时与服务集群 → 网关与发布
  → 指标采集、告警、备份和运维平台。

训练主链：
  目标与基线 → 模型架构 → 代码与配方 → 预检 → 小范围工程验证
  → 提交作业 → 排队与分配 → 启动分布式进程 → 正式预训练
  → 持续评测与检查点 → Base Model。

后续训练链：
  Base Model → 领域继续预训练 / mid-training / 长上下文训练（按目标选用）
  → SFT → DPO、GRPO/RLVR 或 Reward Model + PPO 等对齐路径。
  不把这些算法强行串成所有项目都必须执行的流水线。

交付链：
  候选检查点 → 权重导出与一致性验证 → 能力与风险评测
  → 注册候选模型 → 量化与量化后回归（选用）
  → 预发布服务 → 压测与发布门禁 → 灰度 → 生产服务
  → 监控、回滚、反馈数据治理 → 新的数据版本和新实验。

评测贯穿各训练阶段；性能调优可以返回脚本、数据管线、并行策略或集群配置。历史运行绑定历史输入，不随当前页面的参数修改而改变。

三、完整工程阶段与复刻要求

01 目标、预算和验收基线
  操作：定义模型用途、语言、能力范围、上下文长度、目标 Token 预算、算力预算、质量门槛和推理 SLO；登记对照模型。
  产物：项目规格、评测方案、资源预算、基线评测记录。
  依赖：这些目标用于决定后续数据混合、架构与服务容量。
  复刻规则：未实际运行基线评测时，基线得分为空；不得预先填充“已完成”的实验。

02 工作空间、代码版本和权限
  操作：建立代码仓库、分支、虚拟目录、项目成员、服务账号、训练账号和配额；提交代码，查看差异。
  产物：commit、配置快照、操作审计和资源归属。
  复刻规则：正在运行的作业绑定提交时的代码和配置；修改编辑器中的内容不直接改变运行中进程。

03 原始语料接入与资产登记
  操作：登记对象存储路径、数据源、版本、授权信息、语言、领域与采集时间；创建接入任务；检查文件、记录数、校验和及坏分片。
  产物：Raw Dataset、source manifest、schema、ingestion report。
  复刻规则：区分逻辑数据规模、文件数量、物理占用和可预览样本。TB 级语料以分片清单和元数据表示，浏览器不需要装载同等体量的文本。

04 解析、规范化与质量画像
  操作：解析 HTML、文档及 JSONL；处理编码、不可见字符、模板噪声、重复段落与异常长度；统计语言、长度、领域和质量分布。
  产物：规范化记录、解析失败清单、过滤原因、处理前后统计。
  复刻规则：每条规则都保留输入数、命中数、输出数和配置版本。规则顺序会影响后续命中数。
  依据：Curator 的数据处理工作流将读取、变换、打分过滤和写出组织为可组合阶段。[S03]

05 去重、隐私处理和评测去污染
  操作：精确去重、近似去重、按需要执行语义去重；敏感字段检测与处理；对保留评测集执行重叠检查。
  产物：重复簇、保留/移除映射、脱敏报告、污染检查报告。
  复刻规则：去重应能跨分片识别重复；同一重复簇不得无约束地跨训练集与评测集。需要保留过滤对领域覆盖和 Token 预算的影响。
  依据：Curator 区分精确、模糊和语义去重，不应把它们做成同一按钮的不同名字。[S04]

06 数据切分、混合与版本冻结
  操作：按文档簇、来源、时间或业务分组切分；设置语料混合权重、采样种子、重采样策略；审阅样本并冻结版本。
  产物：train/validation/test 清单、blend 配置、数据卡、数据指纹。
  复刻规则：切分不是机械套用 8∶1∶1；验证和测试集大小按用途配置。测试集在最终比较前冻结。改混合权重产生新版本，不覆写已训练版本。

07 Tokenizer 资产与对话模板
  操作：从头预训练时训练或选定 Tokenizer；继续训练时绑定已有 Tokenizer；检查词表、特殊 Token、编码解码、模板、终止符和长度分布。
  产物：tokenizer.json、tokenizer_config、special tokens、chat template 与版本指纹。
  复刻规则：Tokenizer 变化需要检查词嵌入大小和检查点兼容性；不能当作改一个文本设置而无条件续训。
  依据：分词流程包含规范化、预切分、分词模型和后处理；这些资产属于模型接口的一部分。[S05]

08 训练样本构建和数据工程
  操作：分词、截断、拼接或 packing、生成 position/attention/loss mask、写出分片与索引；测量有效 Token 与 padding 比例。
  产物：训练分片、索引、样本映射、长度直方图、构建配置。
  复刻规则：预训练和 SFT 使用各自正确的数据读取路径。Megatron 预训练的典型产物是 .bin/.idx；SFT 的数据格式和构建方式由选定版本的配置类决定，不能把所有任务强行存为同一种“训练文件”。[S06]
  专业含义：文本大模型中的这一环节包含 Token、模板、mask、packing、采样和分片；不机械套用传统表格模型的特征选择流程。

09 模型架构与初始化
  操作：设定 Dense 或 MoE，检查层数、hidden size、attention heads、KV heads、FFN、词表、RoPE 和上下文；选择随机初始化或导入基座。
  产物：model config、参数统计、初始化来源和架构指纹。
  复刻规则：从零预训练可以没有已有权重；SFT、CPT 和对齐必须明确基座。结构或词表不兼容时导入失败。MoE 另外提供专家数、激活专家数、路由和负载均衡配置。

10 计算、显存与并行规划
  操作：规划节点数、GPU 数、精度、TP/PP/DP/CP，MoE 配置 EP；规划 micro batch、global batch、梯度累积、激活重计算和优化器分片。
  产物：rank 拓扑、每卡显存分项、吞吐和时长计划、配置校验报告。
  复刻规则：显存至少拆分为权重、梯度、优化器/主权重、激活、通信缓冲与运行时余量；同时保留 CPU 内存和存储压力。不能仅用“参数量÷显卡数”决定是否能启动。
  依据：Megatron 的理论估算明确区分模型状态和激活，并列出其未覆盖的碎片、工作区、NCCL 缓冲等因素。[S11]

11 集群、网络与存储建设和验收
  操作：从设备与节点建立起，配置操作系统、网络、身份、存储服务和调度服务；注册计算节点；查看 GPU 型号、显存、驱动、NVLink/PCIe、IB/RoCE、NUMA、网卡；检查共享存储、缓存、带宽和空间；运行通信与 I/O 检查。具体平台建设范围见第十三节。
  产物：节点清单、拓扑、健康报告、通信带宽和存储测试记录。
  复刻规则：节点健康和网络故障影响实际可调度资源；跨节点通信受网络路径影响。维护中的节点不能继续被自动分配。
  依据：NCCL Tests 提供集合通信的正确性与性能测试，适合作为通信验收接口参照。[S17]

12 环境镜像与依赖锁定
  操作：查看容器配方、构建镜像、安装项目包、锁定驱动/CUDA/PyTorch/NCCL/训练框架组合；验证 GPU 可见性、挂载和入口脚本。
  产物：镜像版本与 digest、依赖锁定表、挂载清单、环境检查日志。
  复刻规则：训练、后训练和服务可使用不同镜像，通过明确的模型资产契约交接；不要求所有框架塞进同一个 Python 环境。
  依据：GPU 容器依赖宿主机驱动和相应运行时配置；官方发布的组件版本表应作为兼容组合的依据。[S18][S33]

13 脚本开发、配方与提交前检查
  操作：编辑训练入口、数据构建脚本、YAML、Slurm 脚本与评测脚本；保存、比较差异、提交代码；检查语法、字段、路径、格式和分布式参数。
  产物：代码 commit、已解析配置、提交脚本、预检报告。
  复刻规则：编辑器内容与实际启动配置必须相同；CLI 覆盖值进入最终配置快照；缺包、挂载缺失、错误路径、配置字段错误均在相应阶段报错。
  依据：Megatron Bridge 对预训练与 finetune 使用不同入口条件，并通过配方与统一训练循环执行。[S08]

14 工程验证与性能基线
  操作：用同一模型配置执行短程 smoke test、少量样本的拟合检查、单节点和多节点扩展测试；采集 profiler，验证存取检查点。
  产物：功能验证记录、step time 分解、扩展效率、可启动配置。
  复刻规则：短程验证是一项专业工程活动，不是“小模型版本”。它用于发现数据、loss mask、数值、显存或通信问题，不据此声称大规模训练已经完成。

15 Slurm 提交、排队与资源分配
  操作：使用 sbatch/squeue/sacct/scontrol/scancel；选择 account、partition、QoS、节点约束、GPU 资源和时限；查看 Pending 原因。
  产物：Job ID、提交快照、排队原因、分配节点与会计记录。
  复刻规则：提交成功不等于已经开训；资源不足、配额、依赖和预约影响排队。GRES 的请求类型、数量与后续启动步骤必须一致。[S14][S16]

16 分布式进程启动
  操作：展开节点和 rank，启动工作进程；建立 rendezvous 和通信组；初始化模型、优化器、数据迭代器；检查所有 rank 的准备状态。
  产物：rank 日志、环境变量快照、拓扑映射、启动事件。
  复刻规则：区分调度分配成功、容器启动成功和训练初始化成功；某个 rank 崩溃可能导致其他 rank 等待、超时或共同重启。
  依据：torchrun 负责每个节点上的分布式工作进程，训练代码仍须实现正确的初始化与恢复逻辑。[S10]

17 预训练与继续预训练
  操作：观察 optimizer step、consumed samples/tokens、学习率、训练与验证 loss、grad norm、吞吐、显存、数据耗时和通信耗时；调整配方后创建新运行。
  产物：训练日志、指标序列、检查点、验证结果和运行摘要。
  复刻规则：训练按实际批次、Token 预算和停止条件推进。学习率过高、坏数据、数据供给不足和通信瓶颈造成不同症状；不能让所有配置必然成功或让 loss 永远下降。

18 长上下文与领域训练
  操作：切换领域混合、训练阶段和序列长度；验证位置编码策略、长文数据供给、CP、显存及长上下文评测。
  产物：阶段配置、继承关系、新检查点、通用能力和长上下文回归报告。
  复刻规则：增加 max sequence length 会改变计算和内存压力，并要求相应数据与评测；不等价于输入一个更大的数字就直接获得长文能力。

19 检查点保存、恢复与容灾
  操作：设置保存周期与保留策略；检查分片完整性；停止后重提任务；选择原生恢复或仅加载权重开始新训练。
  产物：模型分片、优化器与调度器状态、RNG、步数、数据读取状态、保存完成标记和兼容报告。
  复刻规则：未完成写入的检查点不能用于恢复。只加载模型权重不会自动恢复全部训练进度。改变并行布局时必须验证检查点与 DataLoader 状态的重分片约束。[S12][S13]

20 SFT 指令微调
  操作：构建多轮对话和工具调用样本；应用模型模板；选择 loss 计算范围、packing、全量训练或适配器；比较基座和训练后模型。
  产物：SFT 数据版本、模板、mask 检查报告、训练检查点或适配器、指令评测结果。
  复刻规则：system/user/assistant/tool 的内容边界和 loss mask 必须可检查。模板、EOS 或 mask 错误可以导致 loss 看似正常但模型行为异常。LoRA 是策略分支，不替代完整的预训练链。[S07]

21 偏好优化与强化学习后训练
  DPO：输入 prompt/chosen/rejected 或等价偏好结构；管理 Policy、Reference 或参考 log-prob 缓存，观察偏好准确率、reward margin、loss 等。
  GRPO/RLVR：从 prompts 生成同组多个 rollout；计算可验证奖励或配置的奖励；归一化优势、更新策略、同步生成权重；观察 reward、KL（启用时）、熵、截断和样本多样性。
  PPO 路径：另外组织 Reward Model 与 Critic 的训练/推理和相关状态。
  复刻规则：DPO 不凭空多出一个必须先训练的 Reward Model；GRPO 不强行要求 Critic；PPO 的组件与数据流单独定义。在线 rollout 的采样、奖励、更新和权重同步具有时间与资源成本。[S19][S20][S21][S22]

22 评测、消融与调优决策
  操作：运行通用、领域、推理、代码、长上下文、指令跟随、工具调用及安全隐私评测；看逐样本结果；对比配方和检查点；分析失败簇。
  产物：固定版本的任务集、模板、few-shot 配置、解码配置、分项结果、样本输出和运行环境。
  复刻规则：比较须对齐评测条件。验证 loss 或偏好 reward 不是全部上线能力的替代。超参数搜索使用验证集作决策；最终测试集保持隔离。
  依据：lm-evaluation-harness 提供任务配置、完整性检查、结果和样本输出等接口，可作为评测工作台的行为参照。[S23]

23 权重转换、导出与模型注册
  操作：从训练检查点导出服务格式；校验配置、分片、Tokenizer、模板和精度；执行固定输入的一致性检查；登记候选版本。
  产物：服务权重、config、Tokenizer、模板、模型卡、依赖、校验和、训练/数据/评测血缘。
  复刻规则：训练框架的原生检查点不直接等同于 vLLM 可加载目录。适配器必须绑定基座及合并/独立加载策略。注册版本不等于已获准发布。[S24][S31]

24 量化、推理配置与服务初始化
  操作：按目标硬件选择精度与量化路径、准备校准数据、执行量化回归；配置 TP/PP、最大上下文、KV Cache、批处理、并发和副本；加载模型并预热。
  产物：量化版本、服务配置、加载日志、缓存容量与健康检查结果。
  复刻规则：权重、运行时和 KV Cache 共同占用显存；量化不会保证无质量损失，也不是所有硬件与内核组合都支持。推理并行布局与训练布局分别配置。[S25][S26]

25 推理调试、压测与发布
  操作：调用模型目录和 Chat Completions 接口；设置 messages、temperature、top_p、输出长度、stream、stop 与工具 schema；执行固定负载压测；查看启动、就绪、存活检查；灰度并比较新旧版本。
  产物：请求记录、流式事件、用量、错误码、TTFT、输出 token 时间、端到端延迟、吞吐、排队、失败率与 SLO 结果。
  复刻规则：容器运行不代表模型已经就绪。改变负载和上下文会影响排队、KV Cache 与延迟。发布版本、路由比例和回滚版本都有明确绑定。[S27][S28][S29]

26 生产运维、反馈与下一轮迭代
  操作：监控 GPU、网络、存储、训练和服务指标；调查告警；扩缩容、下线或回滚；将坏例与反馈送入数据治理和标注流程。
  产物：告警、事件时间线、事故复盘、容量记录、反馈数据集与下一次实验。
  复刻规则：生产反馈先完成去重、标注、质量和污染检查，再进入新版本；不会自动修改已有训练数据和线上模型。资源释放与历史会计记录分别维护。
  依据：DCGM Exporter 的 GPU 遥测与 MLflow 的运行记录是不同层面的观测，平台需要把它们按节点、作业和模型版本关联起来。[S30][S32]

四、必须统一的数据与资产契约

以下字段是本项目的拟定内部契约；不会冒充所有框架都原生使用的统一格式。

1. Project：目标、成员、配额、预算、评测和发布门槛。
2. Source：来源、授权信息、文件清单、记录 schema 和校验和。
3. DatasetVersion：父版本、规则版本、记录/Token 统计、分片、切分与混合配置、指纹。
4. TokenizerVersion：词表、特殊 Token、编码规范、模板与模型兼容信息。
5. CodeRevision：文件快照、commit、依赖和最终解析配置。
6. EnvironmentImage：软件组合、镜像标识、挂载、硬件兼容约束。
7. Cluster / Node / GPU：拓扑、容量、健康状态、分区、分配与占用。
8. Job / Attempt：提交参数、排队原因、分配、退出状态、重试关系、日志与计费时间。
9. Run：训练阶段、算法、代码/环境/数据/模型绑定、指标和检查点。
10. Checkpoint：模型状态、训练状态、数据状态、完成标记与恢复约束。
11. EvaluationRun：模型版本、任务集版本、模板、生成参数、种子、分项结果与样本。
12. ModelVersion：来源 Run、检查点、格式、精度、Tokenizer、评测、别名与发布状态。
13. Deployment：模型版本、服务配置、镜像、健康、容量、路由和发布历史。
14. Event / Incident：时间、来源实体、原因、影响、诊断、修复和关联产物。

数据样本至少区分四类：
  预训练语料：text + doc_id + source_id + 文档元数据。
  SFT：messages 或明确的 prompt/completion，保留角色、工具和监督范围。
  偏好数据：prompt + chosen + rejected，或对应的对话结构。
  RLVR：prompt + 可选参考答案 + verifier / reward 配置；不强塞 chosen/rejected。

应用中显示的大文件、权重和检查点，采用虚拟文件与内容清单记录。校验和、大小、分片和依赖在各视图一致；导出项目包时保存状态、配置、样本与清单，不生成几十 GB 的占位文件。

五、状态机必须对应真实组件

Slurm 的基础状态参考：
  PENDING、RUNNING、SUSPENDED、COMPLETED、FAILED、CANCELLED、
  TIMEOUT、NODE_FAIL、OUT_OF_MEMORY、PREEMPTED 等。
  CONFIGURING、COMPLETING、REQUEUED 等属于状态 flag；不能把所有标签误当成同一层基础状态。[S15]

工作台另外维护作业内部执行阶段：
  环境准备 → 数据挂载 → rendezvous → NCCL 初始化 → 模型加载
  → 优化器加载 → DataLoader 准备 → 训练迭代 → 验证 → 保存 → 清理。
这些阶段不伪造为新的 Slurm 原生状态。

关键行为：
  提交作业只创建 Job 与等待记录；分配后才占用相应 GPU。
  暂停训练是否保留资源、抢占后是否 requeue，由调度策略决定。
  scancel 不无条件保证保存最终检查点；只有已实现信号处理且在宽限时间内完成写入，才能生成新的完整检查点。
  Worker 重启和 Job 重提区分；同一 Run 可以对应多个 Attempt。
  抢占、故障和恢复记录丢失的步数、消耗的 GPU 时间及最后有效检查点。
  新任务不能占用已分配 GPU；后台作业、节点维护和推理副本共享容量约束。

检查点的状态：WRITING → COMPLETE，或 WRITING → INCOMPLETE/FAILED。
模型的状态：CANDIDATE → EVALUATING → QUALIFIED/REJECTED → REGISTERED。
发布的状态：CREATING → SCHEDULING → LOADING → WARMING → READY；同时记录失败和退役。
这里后两组为平台业务状态，不声称是 Kubernetes 的原生枚举。
发布过程再跟踪 Kubernetes 的 Pod phase、conditions、container state、restart count 和 Deployment conditions。

六、参数与结果之间的因果规则

1. Dense 并行关系
  采用所选 Megatron 布局时，DP = world_size / (TP × PP × CP)，结果须为整数。
  MoE 的 EP 作用于专家层，按框架的专家通信组和分片约束校验，不简单把 EP 再乘进所有层的 world_size 公式。[S09]

2. 批次与 Token 计数
  固定批次的一般情况：global batch = micro batch × DP × accumulation。
  TP、PP 和 CP 不作为新增独立样本倍数。
  每次优化器更新分别记录样本数、序列位置数和有效 loss Token 数；packing 或变长序列时不把它们混为一项。
  改梯度累积会改变 optimizer step 频率与有效批次，需要同步检查学习率调度和目标 Token 预算。

3. 显存与性能
  micro batch、序列长度、激活策略、优化器分片和并行布局共同影响显存。
  激活重计算用额外计算换取激活内存；通信、I/O 和保存检查点都可能拉长 step time。
  用明确的分项模型计算虚拟硬件负载，并用固定场景校准关系，不用每个面板各自独立生成随机数。

4. 收敛和泛化
  loss、grad norm、验证曲线和能力结果由算法、数据质量/覆盖、Token 暴露、模型容量、优化器配置与场景种子共同驱动。
  支持发散、loss spike、过拟合、遗忘、奖励投机和评测回归。
  更低学习率、更多 epoch 或更多 GPU 不保证能力单调提升；固定种子下，同一配置重放要一致。

5. 资源、时间和费用
  仿真时间是统一时钟；加速只改变浏览器等待时长，不改变 Token、GPU 小时和历史事件顺序。
  GPU 小时按分配 GPU 数与占用时长累计；资源预留、执行、空闲等待可分项展示。
  费用使用项目设置的费率和计费规则，不把示例费率当成真实云厂商报价。

6. 推理负载
  输入长度、输出长度、并发、到达率、批处理、缓存、精度和副本数共同决定服务状态。
  明确区分 prefill、decode、等待和网络时间；保留不同指标的分母与统计口径。
  压测结果、监控、单次请求和队列长度来自同一执行状态。

七、故障与诊断覆盖

每类故障都应有：触发条件 → 首个可观测症状 → 关联日志 → 诊断操作 → 修复动作 → 恢复后的状态。

数据：
  JSONL 损坏、schema 不匹配、空分片、编码错误、Token 预算不足、重复过多、质量过滤过度、切分泄漏、评测污染、Chat Template/EOS/loss mask 错误。

环境和代码：
  Python 语法错误、依赖缺失、导入失败、配置覆盖错误、镜像拉取失败、GPU 不可见、挂载丢失、权限拒绝、Tokenizer 或模型结构不兼容。

集群和分布式：
  GPU 不足、账号或 QoS 限额、节点 DRAIN/DOWN、rendezvous 地址错误、rank 数量不一致、NCCL timeout、网卡选择错误、跨节点低带宽和 straggler。

训练：
  GPU OOM、CPU OOM、NaN/Inf、梯度异常、坏样本导致 loss spike、DataLoader 饥饿、验证指标恶化、存储写满、检查点部分写入、节点失败、时限到达和抢占。

后训练：
  偏好对格式错误、参考模型不一致、rollout 过期、生成截断、奖励异常、组内奖励无区分、熵下降、策略与生成器权重不同步、奖励上升而能力下降。

推理和发布：
  权重分片缺失、量化内核不兼容、加载 OOM、模板缺失、上下文超限、KV Cache 压力、请求排队、超时、限流、就绪检查失败、灰度回归、回滚目标不可用。

故障处理不能做成“点击修复即可成功”的独立按钮。例：OOM 要通过 batch、长度、并行或内存策略改变来消除；NCCL 网络故障需要修复节点/网络或选择健康资源，改学习率不会解决通信超时。

八、专业工作台的信息结构

1. 项目总览：目标、当前阶段、DAG、预算、最近事件和工程风险。
2. 工作空间：文件树、编辑器、配置 diff、Git、终端和调试输出。
3. 数据平台：数据源、数据集版本、清洗 DAG、质量画像、分片与血缘。
4. 模型配置：架构、Tokenizer、基座、参数、精度和兼容性。
5. 集群资源：节点/GPU/网络拓扑、健康、分区、QoS、配额与占用。
6. 作业中心：提交、排队、运行详情、rank 日志、重试、会计和资源释放。
7. 训练实验：预训练、CPT、SFT、对齐；配置、指标、profiler 和对比。
8. 检查点与模型仓库：分片、恢复、导出、格式、版本、别名和评测绑定。
9. 评测中心：任务集、逐样本结果、消融、模型比较与门禁。
10. 推理服务：部署配置、实例、模型加载、Playground、API 和压测。
11. 监控运维：GPU/作业/请求指标、告警、事件、容量与发布回滚。

这些入口访问同一项目实体。终端中提交的 Job 必须出现在作业中心；界面修改的文件必须能从终端 cat 查看；线上请求必须计入同一服务的监控。

拟支持的命令语义族：
  文件与环境：pwd、ls、cd、cat、head、tail、mkdir、cp、mv、rm、df、du、env、pip、容器命令。
  代码：git status/diff/add/commit/log，python 与 torchrun 的收录工程入口。
  集群：nvidia-smi、sinfo、squeue、sbatch、srun、sacct、scontrol、scancel。
  服务：kubectl get/describe/logs/apply/rollout/scale，curl 的模型和推理请求。
  观测：日志筛选、任务指标、通信检查和 profiler 入口。

命令需解析参数、路径、当前目录、环境变量和退出码；不按整段字符串匹配成功文案。任意 Python/CUDA/Linux 全语义不作为浏览器项目的隐含承诺；未收录语义应给出确定的错误或支持范围，不能假装执行成功。核心工程场景中的命令和脚本结构必须完整覆盖。

九、纯 HTML 的实现边界与状态持久化设计

以下是后续实现方案，本次未开始编写这些业务模块：
  HTML/CSS：专业控制台、IDE、终端、图表和拓扑视图。
  JavaScript：虚拟文件系统、调度器、实体状态、训练/服务事件引擎、配置解析和交互。
  Web Worker：较重的事件计算与重放，避免终端和编辑器卡顿。
  IndexedDB：项目、文件、数据样本、实验、日志和事件；小型偏好设置使用 localStorage。
  导入导出：有 schema version 的项目包、资产清单和校验；支持恢复、迁移和失败回滚。
  离线：业务资产随工程打包，不依赖 CDN 或在线接口。
  单文件交付可内联样式与脚本；运行时持久化须针对 file:// 和 localhost 两种打开方式分别验证。

交互状态流：
  用户命令/界面操作 → 语义解析 → 权限和前置条件 → 事件
  → 更新项目实体与虚拟文件 → 调度/执行状态 → 日志/指标/产物 → 所有视图刷新。

页面关闭后的作业语义必须固定：采用“冻结虚拟时钟”或“按确定性事件补算”之一，不能在没有运行的情况下随意生成结束结果。加速、暂停、恢复、导出、刷新和导入都沿用同一规则。

十一、用于验收 1∶1 行为的场景

A. 完整主线
  A01 创建项目与代码版本，接入多源语料并完成清洗。
  A02 冻结切分、Tokenizer、混合和分片，形成可追溯版本。
  A03 完成集群与镜像验收，建立合法的并行拓扑。
  A04 提交预训练作业，经过排队、分配、启动和迭代。
  A05 保存检查点，完成基座训练和阶段评测。
  A06 从基座进行领域或长上下文训练并比较回归。
  A07 完成 SFT，并从同一候选派生不同对齐实验。
  A08 导出、评测、注册、量化回归、部署、压测和灰度。
  A09 发现质量或 SLO 回归，执行可追溯回滚并建立下一轮数据版本。

B. 资产与一致性
  B01 清洗改动生成新版本；历史 Run、指标和产物保持原绑定。
  B02 提交后修改脚本，只影响下一次提交。
  B03 Tokenizer 或模型结构不兼容时，导入与续训在正确阶段失败。
  B04 删除或损坏检查点分片后，恢复失败且保留原有可用检查点。
  B05 训练完成不会自动出现通过评测或已发布的状态。
  B06 同一对象在终端、文件树、训练页和模型仓库显示一致。

C. 调度与容错
  C01 GPU 不足时排队；其他作业结束后重新计算可运行性。
  C02 节点 DRAIN/DOWN 后，后续分配避开该节点。
  C03 暂停、取消、超时、抢占和节点失败具有各自资源及退出语义。
  C04 在非保存点失败，只从最后完整检查点恢复，不凭空追回步数。
  C05 同一 GPU 不被冲突分配；占用、释放和会计记录一致。

D. 训练与调优
  D01 改 micro batch / 序列长度影响激活显存和吞吐。
  D02 改 TP/PP/CP/DP 必须重新通过整除与模型维度约束。
  D03 梯度累积影响有效批次和 optimizer step，不作为与 micro batch 完全相同的内存旋钮。
  D04 重计算、优化器分片、通信带宽和数据供给呈现不同性能影响。
  D05 OOM、发散、过拟合和训练饥饿具有可区别的日志与曲线。
  D06 同种子同配置可重放；改变时钟倍率不改变最终工程计数。

E. 后训练与评测
  E01 DPO 拒绝错误的偏好结构，且不要求无关的 Critic。
  E02 GRPO 将生成、奖励、优势、更新和权重同步显示为关联执行阶段。
  E03 奖励配置错误可以出现 reward 上升但能力回归。
  E04 评测条件变化留下版本差异，不能默认为公平的直接比较。
  E05 测试污染或模板错误影响评测可信性与发布门禁。

F. 推理与发布
  F01 模型未加载就绪时，请求不会假装成功。
  F02 训练格式未正确转换时服务加载失败。
  F03 更长上下文或更高负载改变缓存、队列、时延和失败率。
  F04 量化/硬件组合不支持时，在加载或校验阶段报告对应错误。
  F05 灰度和回滚改变流量绑定，保留历史请求与评测记录。
  F06 导出导入及刷新后，版本、文件、Job、Run、检查点和发布状态一致。

十二、版本依据与实施前的冻结项

调研使用官方公开文档和项目资料。latest/main/nightly 页面是会移动的资料地址；文档中出现某个功能不等于它存在于每个已发布容器。复刻时需要为每个环境配置固定参考版本或源码快照，并保留来源。

已核查的具体实例：Megatron Bridge 官方组件表列出 NeMo Framework 26.06 对应的 Megatron Core 0.18.0、Megatron Bridge 0.5.0、Transformer Engine 2.16，以及该发布组合内的其他组件。它说明应使用成套版本关系，不能把所有包分别填写“最新版”。[S33]

实施前须形成以下冻结清单（属于后续详细设计输入，不声称本次已完成所有参数级映射）：
  1. 训练、后训练、数据处理、推理四类环境的参考发布版本/源码快照。
  2. 70B 主场景的具体架构配方、集群拓扑、数据与评测场景。
  3. 终端命令参数、返回字段、退出码和脚本结构的支持清单。
  4. 每个故障的触发规则、恢复规则和确定性种子。
  5. 从官方语义到平台实体、状态、文件与页面的逐项追踪表。

阶段结论：完整生命周期、核心组件边界、关键资产、状态关系与行为验收已梳理；下一步是据此建立上述逐项映射和状态模型，再实现工作台。不能跳过这些内容直接制作训练仪表盘。

十三、从空白现场搭建全部系统的补充规格

本节修正将基础设施和平台视为既有条件的不足：它们本身就是必须实现、必须能够建设的工程对象。

责任分为两层：
  开发者负责实现虚拟硬件、操作系统语义、网络、存储、服务、平台、训练和推理的完整运行规则。
  玩家通过第一人称操作进入现场，完成各系统的规划、安装、配置、联调、使用、扩容、排错和维护。
  软件安装与系统建设遵循真实工具的工程语义；不会要求玩家重写 Linux、Slurm 或训练框架源码来完成日常工程部署。

建设对象与验收条件：

P01 工程现场与设备
  创建工位、登录设备、管理服务器、GPU 计算节点、存储节点和交换机。
  配置设备容量、网络连接、磁盘、供电和散热预算；资源清单与机房视图一致。
  验收：设备上电且达到可管理状态；未建立的设备不出现在可用集群列表。

P02 操作系统与基础管理
  完成系统镜像安装或节点部署，配置主机名、磁盘分区与挂载、用户与权限、SSH、软件源、环境变量、进程及系统服务。
  提供包的安装/卸载、服务 enable/start/stop/restart/status、配置文件与本机日志。
  验收：能够登录目标节点并启动基础服务；错误权限、未安装包和无效服务配置产生相应失败。

P03 网络、身份和控制通路
  配置 IP、子网、路由、DNS、时间同步、访问规则、节点认证和跨节点连通。
  管理网络、存储网络、训练通信网络具有独立拓扑与可用性。
  验收：指定服务可解析、可连接、可认证；分辨 DNS 失败、连接拒绝、超时与认证失败。

P04 数据存储与元数据库
  建立本地文件系统、共享存储、对象存储端点、bucket、访问凭据、容量和挂载；初始化平台元数据库。
  实现对象读写、分片清单、文件权限、容量耗尽、服务不可用、备份与恢复的关联行为。
  验收：可从计算节点以正确身份读写数据，文件和对象在相应服务中可见；重启后持久资产保持一致。

P05 GPU 软件栈、容器与镜像仓库
  安装选定驱动与运行时，验证 GPU 识别，建立容器运行环境、镜像仓库、训练镜像和挂载。
  实现依赖、软件版本、镜像构建、拉取、缓存、设备透传和容器进程的状态。
  验收：容器内可用 GPU 数、挂载和所选软件组合满足预检，才能用于训练作业。

P06 集群调度与资源会计
  安装配置控制器、计算节点守护进程、认证和会计组件；定义 Node、Partition、GRES、Account、QoS 和配额；完成节点注册。
  Slurm 参考配置涉及 slurmctld、slurmd、slurmdbd、slurm.conf 等对象；选用 MUNGE 认证时，还需处理密钥、服务与节点一致性。时钟、用户和组的一致性也属于真实建设步骤。[S34]
  验收：节点完成注册并通过健康检查，调度器才能分配资源；控制器故障时区分运行中任务与新任务提交的影响。

P07 数据处理平台
  建立数据接入服务、元数据目录、任务执行器、处理 Worker、清洗规则、DAG 调度、标注与审核工作流。
  数据处理平台自身需要配置存储与元数据库连接、访问权限、Worker 资源和任务入口。
  验收：平台启动且处理 Worker 可用后，才能执行接入、清洗、去重、分词和数据版本发布。只有前端页面可打开不算服务建成。

P08 训练平台、实验追踪与模型仓库
  配置框架包、项目代码、配方、分布式入口、通信环境和检查点路径；启动实验追踪服务及其数据库/制品存储；建立模型仓库。
  训练入口、作业提交、日志采集、指标上报、检查点保存和资产登记分别具有配置和失败状态。
  验收：一次端到端工程验证能够提交、计算、保存、登记并恢复；追踪服务故障不能凭空删除已写入共享存储的检查点。

P09 后训练与评测服务
  建立 Policy、Reference、Rollout、Reward、Critic 等所选算法需要的执行角色；配置资源池、生成运行时、权重同步、奖励环境及评测 Worker。
  验收：各组件能够通过规定的资产与通信接口协作；缺少依赖、权重不一致或奖励服务故障时，任务按对应阶段失败。

P10 推理集群、模型服务和网关
  建立服务集群的控制平面与工作节点，配置容器运行时、节点网络、GPU 资源暴露、存储访问及服务路由；随后部署推理引擎、模型、副本、网关、认证与流量规则。
  Kubernetes 的集群创建涉及控制平面、节点加入和网络等建设步骤，应先于应用 Deployment 的使用。[S36]
  验收：从节点就绪到模型加载、预热、服务就绪逐级通过；端点只有在路由和后端都可用时才能正确处理请求。

P11 观测、告警、备份与持续运维
  安装日志代理、指标 exporter、采集服务、指标存储、看板和告警规则；配置备份目标和恢复流程。
  验收：采集链路真正建立后才出现对应历史观测；没有安装监控时仍可查看本机日志，但不能自动拥有跨集群完整指标。数据源地址或权限错误会表现为采集缺失。

第一人称的交互实现要求：
  玩家可以到达工位、机房和监控现场，在设备或终端上操作。
  工位内的终端、文件编辑器、内部浏览器和管理工具，全部连接同一虚拟系统。
  内部浏览器访问某个平台地址时，需要对应的 DNS/路由/服务满足条件。
  安装系统、修改配置和启动服务会改变设备、网络与应用的真实可观察状态。
  机柜、设备灯、拓扑、终端输出与平台健康来自同一实体，保持一致。

系统依赖的典型传播：
  DNS 配置错误 → 数据存储端点无法解析 → 数据 Worker 读失败 → 数据构建任务失败。
  挂载未建立 → 训练容器看不到数据 → DataLoader 初始化失败 → 不进入训练迭代。
  认证配置不一致 → 节点无法注册/认证 → 集群可分配资源不足 → 作业等待。
  指标采集停止 → 监控出现采集空洞 → 训练是否继续由训练进程和资源状态另行决定。
  推理网关正常、模型实例未就绪 → 入口可访问但业务请求失败 → 不能显示整套服务健康。

补充验收：
  G01 新工程没有自动可用的数据平台、调度集群和推理服务。
  G02 缺少安装包、服务、存储、网络或认证时，阻断对应下游操作。
  G03 按依赖顺序建设各组件后，系统逐步获得相应能力。
  G04 停止某个服务，只影响依赖它的能力；保留不相关运行状态。
  G05 修复配置、重启或重新部署后，可以恢复到一致的工程状态。
  G06 平台建设操作、模型工程操作与第一人称现场，共用一个持久化世界。

工程参考：NVIDIA 的集群部署文档包含存储配置、节点部署、管理节点和调度系统的建设步骤，支持将“基础平台建设”纳入工程主线。[S35] 本节的 P01—P11 是本项目的产品范围和建设验收设计。
